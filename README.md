# مسار — تحديث توافق المرحلة 02 (IDKHAR2.0)

هذه النسخة مبنية على ZIP الأخير، ومخصصة **للقاعدة التي أنشأتها بالفعل** وتحتوي الجداول الستة:
`profiles`, `income_sources`, `expenses`, `goals`, `goal_deposits`, `transactions`.

## الترتيب قبل النشر

1. احتفظ بنسخة احتياطية من قاعدة البيانات الحالية ومن ملفات GitHub.
2. نفّذ `003_add_revision_history_to_existing_schema.sql` إذا لم تكن نفذته سابقاً.
3. نفّذ `004_smart_goal_installments.sql` عبر SQL Editor بعد أخذ نسخة احتياطية. هذا التحديث يضيف جدول الأقساط ودوال تسجيل/إلغاء قسط الشهر.
4. ارفع `index.html` المحدّث إلى فرع تجريبي في GitHub Pages، ثم اختبره قبل نقل التعديل إلى main.
5. تأكد أن `config.js` الفعلي يشير إلى المشروع الصحيح ويستخدم **publishable / anon key** فقط. لم نضف مفاتيح أو أسرار داخل الحزمة.
6. تأكد من Authentication > URL Configuration وأن عناوين إعادة التوجيه تحتوي الرابط الصحيح للموقع.

## تغييرات التطبيق

- التوافق مع `income_sources` بدلًا من `income`.
- مطابقة `due_day` بدلًا من `day` في قاعدة البيانات.
- إضافة `user_id` بشكل صريح عند إنشاء السجلات.
- حساب رصيد الهدف من `initial_amount` بالإضافة إلى إيداعات `goal_deposits`، دون الاعتماد على حقل `current` غير الموجود.
- تسجيل الإيداعات العادية باستدعاء RPC `fn_add_deposit` الموجود في قاعدة البيانات، ثم قراءة الإجمالي.
- إضافة خطة شهرية لكل هدف، مع تسجيل المبلغ الفعلي لكل شهر في رصيد الهدف.
- إعادة توزيع المتبقي على الأشهر غير المكتملة تلقائياً بعد كل إيداع.
- إلغاء إنجاز شهر من وضع تعديل الخطة يعكس الإيداع المرتبط بذلك الشهر ذرياً.
- عدم إرسال حقل رصيد الهدف أثناء التعديل.
- جلب إيداعات الأهداف وعمليات التعديل من القاعدة.
- التحقق من أن الحفظ/الحذف أثر في صف فعلي بدل إعلان النجاح عند عدم تعديل أي سجل.

## نتائج الاختبار وحدوده

- تم فحص JavaScript نحويًا محليًا.
- تم اختبار تحويل أسماء الحقول واستدعاء الدوال بواسطة محاكاة محلية.
- **لم يتم الاتصال بـ Supabase الحقيقية أو إجراء اختبار RLS بين حسابين أو تشغيل ترحيل 004 على قاعدة المستخدم**؛ يجب تنفيذ ذلك على نسخة اختبار أولاً.
- تعديل التاريخ عبر `revisions` يظل منطق الواجهة السابق، وليس سجل تدقيق مالي محصنًا من التلاعب؛ نحتاج لاحقًا نقل تغيير السجلات إلى RPC موثوق.
- إعادة محاولة إيداع بعد انقطاع الشبكة قد تسبب تكرار الإيداع؛ لا تُعد المحاولة تلقائيًا قبل التحقق من السجل، وسنضيف `request_key` فريد في تحديث قادم.
- الحذف الحالي نهائي؛ يجب اعتماد الأرشفة في مرحلة السجل المالي.

**لا تشغّل ملفي LEGACY على قاعدة IDKHAR2.0 الحالية**؛ هما يخصان تصميمًا أقدم ومختلفًا.


## خطة الادخار الذكية

- `004_smart_goal_installments.sql` ترحيل إضافي للقاعدة الحالية، ولا تشغّل ملفات `LEGACY_DO_NOT_RUN_*`.
- عند تسجيل قسط شهر، يطلب التطبيق المبلغ الفعلي (ويقترح القسط الحالي)، ثم تضيفه قاعدة البيانات إلى رصيد الهدف.
- أي إيداع إضافي يعيد حساب المطلوب للأشهر غير المكتملة: (المبلغ المستهدف - الرصيد الحالي) ÷ عدد الأشهر غير المكتملة.
- إلغاء قسط مكتمل متاح فقط بعد تفعيل «تعديل الخطة»، ويُحذف الإيداع المرتبط به داخل معاملة قاعدة البيانات.
